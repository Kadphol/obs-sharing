After deploy, we fly blind.

Your code runs on devices you don't own, networks you can't see, and browsers you didn't test. The only "monitoring" most frontends have:

The support ticket

"Customer says checkout is broken." No URL, no browser, no steps. You try it — works on your machine. Ticket closed. Customer gone.

The vague Slack ping

"Is the app slow for anyone else?" You open DevTools on your M3 Max with fiber internet and see 60fps. Meanwhile a user on a mid-range Android with 3G sees 11 seconds to first interaction.

The backend shrug

Backend dashboards are green. API p99 is 80ms. But the user experience is broken — a render loop, a failed chunk load, a third-party script blocking the main thread. Nobody's graph shows it.

Backend teams solved this a decade ago. The frontend is where it's still dark.

What is observability?

The ability to understand what's happening inside your system by looking at the data it emits — without shipping new code to ask new questions.

Monitoring known unknowns

  • You decide in advance what to watch: error rate, LCP, uptime.
  • Answers "is something wrong?"
  • Dashboards + alerts on predefined thresholds.

Observability unknown unknowns

  • Rich, correlated data lets you ask questions you didn't plan for.
  • Answers "why is it wrong — for whom, where, since when?"
  • "Checkout errors only on Safari 17, only for users with 40+ cart items, started with release 2.4.1."

Monitoring tells you the patient has a fever. Observability lets you run the diagnosis.

Why frontend specifically?

The browser is a production server you don't control

Thousands of device × browser × network × extension combinations. Your staging environment matches none of them. The only place your app truly runs is the user's tab.

Frontend failures are invisible by default

A backend exception hits a log file. A frontend exception dies silently in a user's console and shows up as… churn. No signal, just missing revenue.

Perceived performance is the product

Users don't experience your API latency — they experience time-to-interactive, layout shifts, rage clicks. That's measured in the browser or not at all.

~70%

of user-perceived issues never appear in backend logs — chunk load failures, hydration errors, CORS, third-party scripts, device-specific bugs

1 in 1000

users bother to report a bug. The rest just leave. Instrumentation is how the other 999 file their report automatically.

Five signals, one picture

Each answers a different question. The power is in correlating them — one user session, all five views.

Traces

WHERE did time go?

The journey of one request or interaction, end-to-end, across frontend and backend.

Logs

WHAT happened?

Timestamped, structured events with context. The narrative of your app.

Errors

WHAT broke?

Exceptions captured, grouped, and mapped to source — with the release and user context attached.

Metrics

HOW healthy?

Numbers over time: Core Web Vitals, error rates, API latency from the user's side.

Analytics

WHAT do users do?

Product behavior: funnels, feature adoption, drop-off. Where UX meets business.

The glue: a shared trace_id / session_id stamped on every signal.

Tracing — follow one action end-to-end

A trace is the full story of a single user action — a button click — as it crosses the browser, the API gateway, and every backend service. One trace_id ties it all together.

trace_id: 4bf92f35 — "user clicks Place Order" · total 1.24s

click → checkout.submit
frontend · 1240ms
validate form (JS)
POST /api/orders
network + backend · 770ms
└ orders-svc: create
  └ db INSERT
db · 470ms ⚠
render confirmation
react render · 335ms ⚠

The argument ends here: was it the network, the backend, or our render? The waterfall answers in one look.

Spans — the unit of a trace

A span is one named, timed operation. Spans nest: each has a parent, forming the waterfall. A trace is just the tree of spans sharing one trace_id.

Anatomy of a span

  • name — checkout.submit, HTTP POST
  • trace_id + span_id + parent_id — position in the tree
  • start / end time — the duration bar
  • attributes — cart.items=12, user.tier=pro
  • status & events — OK / ERROR, exceptions, retries

span as data (simplified)

{
  "name":      "checkout.submit",
  "trace_id":  "4bf92f35…",
  "span_id":   "00f067aa…",
  "parent_id": null,          // root span
  "start":     1721286000123,
  "end":       1721286001363,
  "attributes": {
    "cart.items":   12,
    "app.release":  "web@2.4.1",
    "browser.name": "Safari 17"
  },
  "status": "ERROR"
}

Attributes are what make traces queryable: "show me slow checkouts where cart.items > 10".

Tracing in practice — OpenTelemetry

1 · setup once — auto-instrument fetch & page load

import { WebTracerProvider } from '@opentelemetry/sdk-trace-web';
import { FetchInstrumentation } from '@opentelemetry/instrumentation-fetch';
import { registerInstrumentations } from '@opentelemetry/instrumentation';

const provider = new WebTracerProvider();
provider.register();

registerInstrumentations({
  instrumentations: [new FetchInstrumentation({
    // injects the traceparent header → links FE span to BE trace
    propagateTraceHeaderCorsUrls: [/api\.ourapp\.com/],
  })],
});

2 · custom span around business logic

const tracer = trace.getTracer('checkout');

async function placeOrder(cart) {
  const span = tracer.startSpan('checkout.submit');
  span.setAttribute('cart.items', cart.length);
  try {
    return await submitOrder(cart);
  } catch (err) {
    span.recordException(err);
    span.setStatus({ code: SpanStatusCode.ERROR });
    throw err;
  } finally {
    span.end();
  }
}

Magic ingredient: the traceparent HTTP header. Backend picks it up → your click and their DB query share one trace.

Logs — structured, or they're just noise

✗ what we all do today

console.log('checkout failed', err);
// dies in the user's console.
// unsearchable, no context, gone forever.

✓ structured + shipped + correlated

logger.error('checkout.failed', {
  order_id:  order.id,
  user_tier: user.tier,
  release:   'web@2.4.1',
  trace_id:  span.spanContext().traceId, // ← the glue
});

Rules for useful frontend logs

  • Structured JSON, not prose — machines search them, not humans.
  • Event names as identifiers: checkout.failed, not "Oops something went wrong!!"
  • Always attach trace_id, session_id, release.
  • Sample & batch — don't fire a network request per log line; buffer and flush.
  • Never log PII — emails, tokens, card data. Scrub at the source.

The payoff

Error dashboard shows a spike → click through to the trace → see the logs of that exact session, in order. Debugging goes from archaeology to reading a story.

Error tracking — the 999 silent reports

What a real error tracker adds over try/catch

  • Global capture — onerror, unhandled rejections, React error boundaries.
  • Grouping — 40,000 events → 12 distinct issues, ranked by users affected.
  • Source maps — a.min.js:1:48211 becomes Checkout.tsx:57. Non-negotiable: upload them in CI.
  • Release tracking — "introduced in web@2.4.1" → instant suspect: that release's diff.
  • Context — browser, OS, breadcrumbs (last N clicks/requests before the crash).

sentry (or glitchtip / bugsnag / rollbar) — 10 lines

Sentry.init({
  dsn: 'https://…@sentry.io/123',
  release: 'web@2.4.1',        // match your CI tag
  environment: 'production',
  tracesSampleRate: 0.1,       // perf traces, 10%
  beforeSend(event) {
    return scrubPII(event);     // your gate
  },
});

// React: catch render crashes gracefully
<Sentry.ErrorBoundary fallback={<CrashScreen />}>
  <App />
</Sentry.ErrorBoundary>

If you adopt only one thing from this talk, adopt this. Highest value ÷ effort in observability.

Monitoring — Real User Monitoring & Web Vitals

Core Web Vitals — the user's stopwatch

  • LCP — Largest Contentful Paint · "when did the page look ready?" · good < 2.5s
  • INP — Interaction to Next Paint · "did my click respond?" · good < 200ms
  • CLS — Cumulative Layout Shift · "did the page jump under my finger?" · good < 0.1

Lab vs field

Lighthouse = lab: one synthetic run, your hardware. RUM = field: distribution across every real user. You need the field data — track the p75, not the average, and segment by device & country.

web-vitals — the whole integration

import { onLCP, onINP, onCLS } from 'web-vitals';

function send(metric) {
  navigator.sendBeacon('/rum', JSON.stringify({
    name:   metric.name,        // 'LCP' | 'INP' | 'CLS'
    value:  metric.value,
    rating: metric.rating,      // 'good' | 'poor'…
    page:   location.pathname,
    release: 'web@2.4.1',
  }));
}

onLCP(send); onINP(send); onCLS(send);

Then: dashboard the p75 per page, alert when a release regresses it. Perf stops being vibes.

Analytics — observability for product behavior

Different question, same discipline

Observability asks "is the system healthy?" Analytics asks "are users succeeding?" A checkout can be error-free, fast — and still lose 60% of users on step 2. That's a product bug no error tracker will file.

What to track (and what not)

  • Events, not pageviews: checkout.step_completed, search.no_results.
  • A tracking plan — a reviewed schema, same rigor as an API contract. No free-form event names.
  • Funnels & session replay (PostHog, Amplitude, GA4) — replay pairs beautifully with error tracking.
  • Consent & PII: respect the cookie banner, anonymize IDs. PDPA/GDPR apply to us, not just legal.

the crossover superpower

// same session_id across ALL signals
analytics.track('checkout.step_completed', {
  step: 2,
  session_id: sid,   // ← joins analytics…
});

logger.info('payment.method_selected', {
  session_id: sid,   // ← …to logs…
  trace_id: tid,     // ← …to traces & errors
});

Now you can answer

"Users who hit the payment.timeout error — how many completed checkout later? Which step did the rest abandon?" Engineering data meets product data.

Adoption roadmap — crawl, walk, run

Week 1 · crawl

See the crashes

  • Error tracker SDK in production
  • Source maps uploaded in CI
  • Release tagging on every deploy
  • One React error boundary at app root
  • Alert to Slack: new issue / regression
Month 1 · walk

See the experience

  • web-vitals beacons → dashboard p75 per page
  • Structured logger util, replace stray console.log
  • Product events for the 1 critical funnel
  • Perf budget check in CI (bundle size, LCP)
Quarter · run

See the whole story

  • OTel tracing with traceparent → backend
  • trace_id stamped on logs + errors + events
  • Session replay wired to error issues
  • Dashboards per team, alerts on p75 regressions

Each step ships value alone. Don't wait for the grand unified platform to start step 1.

If you remember five things

01  The browser is production. Instrument it like you'd instrument a server.

02  Users don't file bugs — SDKs do. Error tracking first; it pays for itself in a week.

03  A trace is a tree of spans; the traceparent header joins your click to their DB query.

04  Correlation beats collection: trace_id + session_id on every log, error, and event.

05  Measure the field, not the lab — p75 of real users, segmented, per release.
